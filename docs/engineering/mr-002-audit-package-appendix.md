### Deviations from the frozen requirements, as reported

1. 1. FROZEN SIGNATURE CHANGED — Validate takes schema.RecordKind, not loader.RecordKind. internal/knowledge/loader/loader.go:27 already imports internal/knowledge/schema, so `func (v *Validator) Validate(kind loader.RecordKind, ...)` closes an import cycle and does not compile. I took the brief's option (a): schema declares its own `type RecordKind string` with KindDecision/KindInvariant spelled identically, and callers convert with schema.RecordKind(ref.Kind) at the call site in `validate`. Option (b) (plain string) was rejected because it discards type safety at the one place two same-shaped string types meet. The cost of (a) is that a conversion between two string types is silent when the strings drift, so TestSchemaKindsAreSpeltTheSameWayAsTheLoaders (validator_test.go:448) asserts the equality directly — an external test package may import loader without a cycle. Mutation M14 confirms it goes red.

2. 2. Finding LIVES IN `schema`, AND IS A DIFFERENT, NARROWER TYPE THAN THE DESIGN'S validate.Finding. The design puts Finding in `validate` but has schema.Validate return []Finding; validate imports schema, so schema cannot import validate. Resolution: schema.Finding{InstanceLocation, Keyword, Message} — it carries no Path, ID, Step, Code or Fatal, because none of those are facts this package has. validate.Finding as frozen in design §3 is untouched and remains TASK-05's to declare; TASK-05 builds one from each schema.Finding, adding Path/ID from the RecordRef, Step=StepSchema, Code=CodeKnowledgeInvalid, Fatal=false. Both types will exist and neither shadows the other.

3. 3. NEW EXPORTED API not named in the frozen design, all in package schema: RecordKind, KindDecision, KindInvariant, Finding, ErrSchemaNotShipped, KeywordDocumentSyntax, KeywordNoSchema, SchemaNameFor. ErrSchemaNotShipped is a sentinel rather than a message because tech-stack §72 forbids control flow on error text and because the library's *LoadURLError implements no Unwrap (see mutation M12).

4. 4. kind.AdditionalProperties is reported as ONE FINDING PER OFFENDING PROPERTY, located on the property itself, rather than one finding located on the parent object. AC-02.7 requires the message to name the offending property; the library already does that in its own wording, so a message-only fix would have been untestable (right and wrong answers both contain the property name). Splitting makes the name structurally reachable. Consequence to know: a record with N extra properties yields N findings, not 1. AC-02.6's 'six findings' fixture has exactly one extra property, so the stated count is unaffected.

5. 5. NewValidator REQUIRES EVERY REGISTRY DOCUMENT TO DECLARE A `$id`, which is stricter than the registry's existing 'extra documents are kept so a future schema version can ship alongside v1' promise. AC-02.2 says every document in the registry is registered with AddResource($id, doc), and a document with no $id has no url to be registered under; registering it under an invented one would create a resource no $ref could name. Note this makes NewValidator reject the fixture used by the pre-existing TestNewRegistryAcceptsExtraDocuments (a bare `{"$schema":...}`), though that test does not call NewValidator and still passes unedited. TestValidatorAcceptsAnExtraSchemaDocumentAlongsideV1 (validator_test.go:331) is the over-fire guard proving a well-formed future document still does not break a v1 binary.

6. 6. Documents are registered under their OWN $id but compiled under a Go-pinned constant (schemaIDBase + name). Both are the same string for the shipped documents (asserted by TestShippedSchemaDocumentsDeclareThePinnedID), so AC-02.2's 'same $id string' holds. The pinning is what makes AC-02.2's other clause non-vacuous: registering and compiling the document's own $id would make 'rejects a document whose $id was not registered' impossible to fail (mutation M6 demonstrates exactly that).

7. 7. registry.go's PACKAGE DOC WAS REWRITTEN. It asserted 'it deliberately does not compile or evaluate the schemas (decision D-28). Compiling them is MR-002's job', which this change makes false. Doc-only edit, no code touched; the D-28 split it describes is preserved in the new wording.


### Risks flagged

- TASK-05 must convert at the call site: `v.Validate(schema.RecordKind(ref.Kind), ref.SchemaVersion, ref.Body)`. The conversion is silent if the two constant sets ever drift, so if you add a third record kind add it to BOTH loader.kindDirs and schema.validatedKinds and to the table in TestSchemaKindsAreSpeltTheSameWayAsTheLoaders.
- D-47 says Check sorts by (Path, Step, InstanceLocation, Message), but the frozen validate.Finding carries no InstanceLocation. Sort while you still hold the schema.Finding, or thread InstanceLocation through. schema.Validate already returns findings sorted deterministically WITHIN one document, so Check only needs a stable outer ordering across records — but do not rely on that alone: the sort key inside Validate is (InstanceLocation, Keyword, Message), not the one D-47 names.
- schema.Finding.Keyword can be one of two non-keyword sentinels: KeywordDocumentSyntax (bytes that are not a single JSON value) and KeywordNoSchema (no compiled schema for that kind/version, or an unexpected error type). Whatever TASK-05 renders must not assume Keyword is a real JSON Schema keyword. In practice KeywordNoSchema should never fire from the real pipeline, because loader step 4 already fatals a version outside the reader window — if it ever does, it is a programming error, not a repository condition.
- Validate returns an EMPTY NON-NIL slice for a clean record (guarded by mutation M10), so Check can append without a nil check. Do not change that without updating TestValidatorAcceptsARecordThatSatisfiesItsSchema; AC-03.9 wants the same property of Check.
- NewValidator returns an error, and AC-08.2 says a failure there is a defect in the binary and must not be reported as a repository condition. Do not let bootstrap fold it into KnowledgeErr (D-42 forbids that for findings; this is a different, harder failure that halts nothing the loader did).
- A Validator is safe for concurrent use (compiled *jsonschema.Schema is read-only after Compile; Validate keeps no state). The `loader *deniedLoader` field is written only during construction; if a later change makes anything call the loader after NewValidator returns, that field stops being race-free and TestNewValidatorResolvesEverySchemaWithoutAFetch is where you will notice.
- SchemaNameFor derives "<kind>.v<n>.schema.json". If the reader window ever widens past [1] without a matching document shipping, NewValidator fails at startup by design — that is the intended failure, not a bug to route around.
- bin/mindrail was produced by `make build` for the binary-exists check; it is gitignored (.gitignore:38 `/bin/`). /tmp/mrprobe and /tmp/mrprobe/probe2 hold the two library probes and /tmp/validator.go.orig the mutation-sweep baseline — all outside the repo, none referenced by anything.

### Deviations from the frozen requirements, as reported

1. 1. NewInvariant's third parameter is REFUSED when non-empty, rather than stored or dropped. The frozen signature (design §3, AC-01.2) is `NewInvariant(id string, at time.Time, title, statement string, opts ...Option)`, and invariant.v1 declares no `title` property and sets additionalProperties:false. Storing it would make every record the constructor produced fail step 5; dropping it would lose the caller's data in silence — the exact class MR-001 paid for. So the fourth parameter becomes `statement` and a non-empty third returns ErrInvariantHasNoTitle, naming the statement as where the prose belongs. RECOMMENDATION, as the brief asked me to state: the honest signature is `NewInvariant(id string, at time.Time, statement string, opts ...Option) (Invariant, error)`. I did NOT take it, because AC-01.2 freezes the four-parameter form and an independent audit grades against that; changing a frozen signature unilaterally is what the requirements document exists to prevent. If the orchestrator wants the change, mutation M34 shows exactly what breaks: only the assertion at record_test.go:25, plus the removal of the ErrInvariantHasNoTitle branch and its test.

2. 2. Supersede returns (replacement, prior) — the REVERSE of its parameter order. Both design §3's comment ('returns the pair the caller must write: the replacement carrying supersedes, and the prior record with its status moved') and AC-01.4 enumerate them replacement-first, so that is what I implemented. It is a genuine trap: both returns are Decision, so a call site that binds them the other way round compiles and would write each record over the other's file. The doc comment names it as a trap and TestSupersedeReturnsTheReplacementFirstAndMovesThePrior identifies each return structurally rather than positionally. Flagged again under risks.

3. 3. Invariant.Scope is a VALUE (`Scope Scope `json:"scope"``), not a `*Scope`, while Decision.Scope stays `*Scope` as the design freezes it. This is not symmetry-breaking for its own sake: invariant.v1 lists `scope` in `required` and decision.v1 does not. A `*Scope` with no omitempty marshals a nil as `null`, which is a document asserting absence in the one place absence is forbidden. A value cannot be absent, so the Go type carries the requirement instead of merely hoping a constructor enforced it. TestStructsMirrorTheirSchemaDocuments derives the expectation from each document's own `required` list, so this stays honest if either document changes.

4. 4. NEW EXPORTED API not named in the frozen design, all in package record: Severity + SeverityCritical/High/Medium/Low; ScopeLevel + ScopeProject/Package/Module/File/Symbol; KindDecision/KindInvariant; Option and the seven With* constructors; sixteen Err* sentinels; the three typed errors EmptyFieldError, OptionKindError, DuplicateItemError; and `(Scope) Validate() error`. The design froze `type Invariant struct { /* mirrors the invariant.v1 schema */ }` and `opts ...Option` without spelling either out, so this surface is the resolution of those placeholders. `Scope.Validate` is exported deliberately — see risks.

5. 5. The constructors are STRICTER than the pipeline in exactly one place: a PROJECT scope carrying a target is refused (ErrScopeTargetOnProject). AC-03.4 does not list that among step 11's conditions, so `Scope.Validate` — the function step 11 should call — deliberately does NOT refuse it, and a record already on disk with one must not become a finding. The extra rule lives in the constructor's checkScope, is commented as writer-side, and is justified by the schema's own description of `target`: 'Absent for PROJECT scope'. This is a writer-strict / reader-lenient split, stated so an auditor does not have to infer it.

6. 6. Constructors also refuse two things the JSON Schema alone would accept, both to make AC-01.5's property true: a zero `created_at` (well-formed as a date-time, but a record dating itself to year one is a caller who forgot the clock, and no later validation can detect it), and a record whose `supersedes` names its own id (permitted by the schema, but a closed walk of length one — spec §95 step 9's cycle, which D-39 makes fatal).

7. 7. `graphify update .` was NOT run, despite CLAUDE.md's post-modification rule. The brief's scope instruction ('Touch only internal/knowledge/record/ ... if you believe you need to edit a file outside that directory, do not') overrides it, and regenerating graphify-out/ while a parallel agent is mid-edit in internal/knowledge/loader/ would bake a half-finished tree into the graph. Recorded for the orchestrator to run once the wave lands.

8. 8. The round-trip encoder lives in the test, not in the package. 0.1 ships no writer (design §1: MR-014 owns the agent-facing write path), so there is nothing in `record` for the goldens to serialize through. AC-01.6 does not say who owns the encoder, and exporting one would be more invented API. The consequence for MR-014 is recorded under risks.


### Risks flagged

- Supersede's RETURN ORDER IS (replacement, prior), the reverse of its parameters, and both returns are Decision — a swapped call site COMPILES. Bind by name: `carrying, superseded, err := record.Supersede(prior, replacement)`. This is the single most likely way wave 3+ silently writes each record over the other's file.
- TASK-05's step 11 should call `record.Scope.Validate()` rather than write a second implementation of the scope-syntax rule — two implementations of one rule is precisely the drift D-36 exists to prevent, and the schema documents cannot express this rule so there is no third authority to fall back on. ### Deviations from the frozen requirements, as reported

1. 1. THE FROZEN SIGNATURE OF schema.Validate — I respected wave 1's change rather than the design's letter. Design §3 freezes `Validate(kind loader.RecordKind, ...) []Finding` with Finding in `validate`; TASK-01 could not implement that (loader imports schema, so loader.RecordKind closes a cycle) and shipped `Validate(schema.RecordKind, int, []byte) []schema.Finding`. So validate converts at the call site with `schema.RecordKind(s.ref.Kind)` (steps.go, stepSchema) and declares its own validate.Finding exactly as design §3 froze it. Both Finding types now exist and neither shadows the other. Recorded here because an auditor reading the design will expect one type and find two.

2. 2. exitForCode[CodeKnowledgeInvalid] = app.ExitSuccess, NOT app.ExitFailed as the brief suggested. The brief said the KindFailed fall-through (exit 1) 'is the right class here' for both codes; the FROZEN requirements document's own D-43 table says KNOWLEDGE_INVALID is StateDegraded at exit 0 and only KNOWLEDGE_SUPERSEDE_CYCLE is StateError at exit 1. I followed D-43, because the audit grades against the frozen document and because ExitSuccess in that table means something specific and checkable — 'this code must never appear in an error object at all' (envelope_test.go's assertEnvelopeCoherent t.Fatals if it does). A DEGRADED doctor reading never reaches errorFrom, so ExitSuccess is the assertion that a repository with one malformed Decision stays usable. If TASK-06 wires KNOWLEDGE_INVALID onto anything that becomes an error object, this row is what will fail — deliberately.

3. 3. kindForCode WAS NOT GIVEN AN EXPLICIT CASE, and the brief asked me to say which I found. The fall-through IS sufficient: nothing in the tree enumerates RegisteredCodes() against kindForCode, so neither the compiler nor any test demands a case. app.KindFailed is correct for KNOWLEDGE_SUPERSEDE_CYCLE and unreachable for KNOWLEDGE_INVALID, which is exactly the position of the two existing zero-exit codes (WORKSPACE_NOT_INITIALIZED, CONFIG_UNKNOWN_ENV_VAR), neither of which has a case. Adding one would be a branch returning the same value as the default — a guard no mutation could falsify, which is the class MR-001's second audit round was spent removing. I recorded the reasoning in the doc comment instead. Note this means AC-05.2's kindForCode half is satisfied by the default arm, not by a named case; if the auditor reads AC-05.2 as requiring a literal `case`, this is the line to argue about.

4. 4. STEP 6 IMPLEMENTS THE ID HALF ONLY. AC-03.4 says step 6 detects a 'filename<->kind/id disagreement'. The kind half is structurally discharged by step 5: the loader takes a record's kind from its directory (loader.go:48-57), step 5 validates against THAT kind's document, and both documents pin `kind` with a `const`. So a record filed in invariants/ that calls itself a decision fails step 5, and D-40 then means step 6 is never asked about it — the kind rule is unreachable at step 6 by construction. Re-implementing it in Go would be the second implementation D-36 forbids AND dead code. TestAKindThatDisagreesWithItsDirectoryIsReportedByStepFive (steps_test.go:460) asserts the Step, so an implementation that moved the rule into step 6 fails.

5. 5. AC-03.4's step-11 'level is not one of the five' CLAUSE IS UNREACHABLE THROUGH Check, for the same D-40 + D-36 reason: both documents pin the level with an enum, so step 5 rejects a bad level first. step 11 still calls record.Scope.Validate, which does refuse it, so nothing is omitted — but no store can make step 11 report it. TestAScopeLevelOutsideTheEnumIsReportedByStepFive (steps_test.go:486) states this as a fact rather than leaving it as a silent gap. Step 11's other two clauses are reachable and tested.

6. 6. CHECK PANICS ON A NIL VALIDATOR rather than returning early. There is no honest alternative available to me: returning no findings publishes 'nobody looked' as 'we looked and it is clean', and no registered code says 'this binary could not build its own validator' — AC-08.2 makes that a defect in the binary that bootstrap reports as such, and REQ-05 freezes exactly two new codes so I could not add one. TestCheckRefusesANilValidator (validate_test.go:489) makes it a decision rather than an accident. TASK-06 must not call Check when schema.NewValidator failed.

7. 7. STEP 10 COUNTS ACTIVE IDS PER LINEAGE, NOT ACTIVE FILES. Two files carrying one id are step 7's condition; counting them again at step 10 would give one condition two diagnoses, and it would fire on the exact fixture MR-001 left behind (the duplicated DEC-9999 in TestLoadDoesNotPerformMR002Validation), which is a naming mistake and not a forked lineage. Mutation M19 is the proof this is load-bearing.

8. 8. D-45 STEP 10, THE CONSERVATIVE READING. Lineage edges point only at ids that resolve to a record that was read, so two records both superseding ONE UNREADABLE id are reported as two lineages, not one fork. A case can be made the other way — the fork is provable from the two records that were read — but D-45's step-10 clause says not to claim a duplicate active lineage when the disambiguating record is unreadable, and this is the reading that never publishes a claim resting on a file the loader already said it could not read. It is pinned by the fourth suppression row, WITH its readable positive control, so the choice is visible rather than buried. Flag this if the auditor reads D-45 the other way; it is one predicate in lineage.go's newGraph.

9. 9. I EDITED TWO FILES OUTSIDE MY PACKAGES. internal/cli/envelope_test.go (required by AC-05.2 — the table lives in the test package) and internal/doctor/check.go (COMMENT ONLY, no code change: `git diff` shows 13 lines, all inside kindForCode's doc comment). Neither is TASK-06's or TASK-07's code.

10. 10. THE LOADER'S FIXTURE JSON IS COPIED, NOT SHARED, in pairing_test.go. loader_test.go's decisionJSON lives in package loader_test and no other package can import it. The copy is made safe by running the REAL loader over it in the same test and re-asserting the loader's own half (Problems==0, Count()==3), so a change to the loader side turns this test red too.

### Risks flagged

- NO PRODUCTION CODE CALLS validate.Check YET. The package is reachable only from its own tests, which is why the whole suite and every golden stayed green without regeneration. TASK-06 wiring it into bootstrap is what will move doctor/status output and force the AC-09.6 golden regeneration.
- Check PANICS on a nil *schema.Validator. AC-08.2 already requires bootstrap to treat a schema.NewValidator failure as a defect in the binary; the consequence of getting that wrong is now a panic, not a silent clean report. Do not fold the NewValidator error into KnowledgeErr (D-42 forbids that) and do not call Check on that path.
- A CYCLE PRODUCES ONE FINDING PER MEMBER, not one per cycle. A two-record cycle is two findings, both Fatal, both carrying the same rotated chain in their message. doctor's `findingRemedies` should deduplicate by chain or by Code when it renders, or a three-record cycle prints the same sentence three times. Likewise step 7 emits one finding per file in the duplicate group and step 10 one per active record.
- THE CODES ARE REGISTERED BUT NOT YET EMITTED BY ANY PRODUCTION PATH. I checked for a test asserting every registered code is reachable from the CLI, as the brief asked: THERE IS NONE. app.RegisteredCodes() is read only by internal/app/code_test.go:25, internal/app/errors_test.go:122 and internal/cli/envelope_test.go:58, and envelope_test only checks that a code which DOES appear has a table entry. So nothing fails today because KNOWLEDGE_INVALID and KNOWLEDGE_SUPERSEDE_CYCLE are unreachable — wave 4 is what makes them reachable, and wave 5's AC-09.2 agreement rows are what will prove it.
- exitForCode[CodeKnowledgeInvalid] = app.ExitSuccess is a live constraint, not a formality: assertEnvelopeCoherent t.Fatals with 'reached the wire as a fatal error' if any command ever puts KNOWLEDGE_INVALID in an error object. If TASK-06 makes a non-fatal finding block readiness or produce an error envelope, that is the test that fires — and per D-43 and AC-07.5 the right fix is the wiring, not the table.
- validate/paths.go SPELLS THE STORE LAYOUT A SECOND TIME (recordSuffix = ".json" and kindDirs {decision: decisions, invariant: invariants}), because loader's copies are unexported. TestTheExpectedPathIsTheOneTheLoaderProduces (validate_internal_test.go:34) is the ONLY thing holding them together, and if they drift, D-45's suppression silently stops matching and step 8 starts reporting 'does not exist' for files the loader already named. A third record kind must be added to loader.kindDirs, schema.validatedKinds, record's constants AND validate.kindDirs.
- STEP 9's CYCLE DETECTION IS RECURSIVE (graph.cycles uses a recursive closure). Depth is bounded by the number of distinct record ids, which is fine at 0.1's scale — the loader's own stress test uses 50 records — but a store of many thousands of records in one long chain would risk the goroutine stack. If MR-005 or later widens the expected store size, convert it to an explicit stack.
- record.Scope.Validate returns FOUR sentinels but step 11 routes only three of them; the fourth, record.ErrScopeTargetOnProject, is deliberately NOT returned by Scope.Validate (it is a writer-side rule the constructors enforce separately). Do not add it to step 11: AC-03.4 does not list it, and a record already on disk carrying a PROJECT scope with a target must not become a finding.
- AC-01.5's fixture had to flip an Invariant's Status by hand, because record.Supersede covers Decisions only and there is no SupersedeInvariant. Anything that writes an invariant lineage (MR-014) will hit the same gap, and a lineage whose older member is left active is a real step-10 finding.
- Left outside the repository, referenced by nothing: /tmp/mr002-t05/ holds the mutation baseline (a copy of the eight validate .go files plus code.go.bak and envelope_test.go.bak), the two drivers mutate.py and mutate2.py, and final-test.txt. The drivers restore the tree after every mutation and I verified with `git status` and a full green run that they did; they can be deleted.
- `graphify label` is owed if the community names matter: `graphify update .` reported that the community set changed (206 saved labels, 192 communities now, 53 renamed by their hub) and asked for a relabel. I did not run it because it costs an LLM call.

### Deviations from the frozen requirements, as reported

AC-08.2 requires it be reported as a defect in the binary, 'not as a repository condition, and not silently swallowed'.
